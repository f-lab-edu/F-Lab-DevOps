# A5 엔진 선정과 실제 AI 연결: 완료

- 확인일: 2026-10-01
- 범위: 로컬 합성 증거를 대상으로 한 읽기 전용 조사. 라이브 EKS 조회·운영 조치·프로덕션 데이터 전송은 포함하지 않는다.
- 상태: **A5 완료, 현재 엔진은 OpenAI Responses 어댑터.** 개발용 합성 사례 다섯 건의 실제 AI 보고서 생성·근거 인용·감사 기록, 실패 실행의 알려진 부분 사용량·안전한 계약 오류 기록, S2 정상 miss 재검증을 확인했다. 계획했던 HolmesGPT의 4~6건 동등 조건 품질 비교는 API 호환성 조건을 충족하지 않아 수행하지 않았으며, 그 한계와 선택 근거를 아래에 기록한다.

사용자는 API 키 방식을 선택해 키를 개인 저장소에 입력했고, **Plus 구독 연동 경로는 사용하지 않기로 확정했다.** 첫 실제 호출은 크레딧 부족으로 거부됐고, 결제 후 재검증에서 개발용 합성 사례 다섯 건의 보고서 생성에 성공했다. [ChatGPT Plus 연동 가능성](A5-plus-feasibility.md)은 비채택 검토 기록으로만 남긴다. Plus 경로 구현은 A5 완료 조건이 아니다.

## 엔진 결정 기록

HolmesGPT를 우선 조사했다. [0.42.0 Python SDK](https://github.com/HolmesGPT/holmesgpt/blob/0.42.0/docs/reference/python-sdk.md)는 `additional_toolsets`로 사용자 Python 도구를 주입하고 `max_steps`, 태그 필터, 자동 도구 활성화 여부를 설정할 수 있다. 실제 설치 버전에서 A4의 여섯 조회 함수만 노출하고 내장 bash·Kubernetes·인터넷 도구를 제외하는 구성을 다섯 합성 입력에 대해 확인했다. 다만 이 설정만으로 모델 호출·증거 ID·전체 시간·건당 비용 경계가 기존 실행기와 동일하게 강제된다는 뜻은 아니다. [공식 사용자 도구 문서](https://github.com/HolmesGPT/holmesgpt/blob/0.42.0/docs/data-sources/custom-toolsets.md)의 YAML 도구는 셸 명령을 사용하므로 이 프로젝트의 읽기 전용 경계에는 그대로 연결하지 않는다.

현 로컬 단계에서는 작은 **OpenAI Responses 어댑터**를 A5 엔진으로 선택한다. [Responses 함수 호출 문서](https://developers.openai.com/api/docs/guides/function-calling)에 따라 모델에는 A4 함수 여섯 개만 공개하고, 실행은 A4의 `query_bundle`과 `run_replay`가 담당한다. 모델에 임의 shell·Kubernetes 쓰기·호스팅 도구를 제공하지 않는다. 선택 기준은 동일한 개발 입력·읽기 전용 도구·권한·시간·비용 아래의 진단 품질과 증거 추적·제한 강제·재현성·운영 복잡도다. 설치한 HolmesGPT 0.42.0의 표준 모델 경로는 LiteLLM의 Chat Completions를 호출했다. [GPT-6 Sol 모델 문서](https://developers.openai.com/api/docs/models/gpt-6-sol)는 Chat Completions의 함수 호출을 `reasoning_effort: none`에서만 지원하며, 현재 어댑터의 Responses + `low` 설정과 같은 조건을 만들 수 없다. 따라서 계획했던 동등 조건 4~6건 품질 비교의 전제 조건이 성립하지 않는다. A5에서는 이를 호환성 검증 결과로 기록하고, 이미 실제 보고서와 경계 검증을 통과한 어댑터를 선택한다. 이 결론은 HolmesGPT 전체 기능의 부재나 다른 모델·브리지 구성의 불가능성을 뜻하지 않는다. 고정 최종 평가 입력은 엔진 선정에 사용하지 않는다.

이 프로젝트의 `reasoning.effort: low`는 **운영 조사 모델에 보내는 API 설정**이다. 구현 작업에 권장하는 Codex의 `high` 추론 깊이와는 별개다. 운영 조사 모델 양쪽을 `high`로 바꾸더라도 HolmesGPT 0.42.0의 표준 Chat Completions 경로에서는 함수 호출이 지원되지 않는다. `high`로 동등 비교하려면 HolmesGPT 쪽도 Responses 경로로 연결하고, 현재 어댑터도 `high`로 바꾼 뒤 비용·시간·증거 제한을 다시 검증해야 한다. 설정값만 바꿔 이미 검증한 A5 결과를 대체하지 않는다.

요청 본문은 계속 16,000바이트로 제한한다. 실제 모델 호출 전에는 [Responses 입력 토큰 수 API](https://developers.openai.com/api/docs/guides/token-counting)로 같은 입력·지시·도구의 토큰 수를 세고 최대 출력 토큰과 합산해 건당 예산을 선점한다. 모의 전송 시험은 이 API 없이 보수적인 바이트 수를 사용한다. 이 계산은 가격·캐시·청구 방식의 변화까지 포함하는 절대적인 청구 상한은 아니다. 응답 usage를 읽어 같은 표준 단가로 추정 비용을 기록하며 usage가 없으면 성공으로 처리하지 않는다. 일일 예산 파일 `ai-budget.json`은 개인 `--store` 안에 0600으로 둔다. 같은 저장소에서 계정 별칭을 바꿔도 UTC 날짜별 한도가 공유된다.

## 처리 흐름과 검증

`investigate --mode ai`는 등록 대상·묶음 hash·질문을 검증하고 일일 예산을 선예약한다. 모델은 사건 질문과 증거 카탈로그를 먼저 받는다. 함수 호출을 선택하면 A4가 범위·인자·런북 hash를 확인해 반환하며, 이후 호출에서 실제 제공된 증거와 런북만 모델이 본다. 최종 JSON은 `AnalysisReport` 계약으로 검증한다. 관측 사실, 원인 가설, 반대 근거, 누락 자료, 추가 확인, 미실행 제안을 구분하고, 모델이 실제 전달받지 않은 증거 ID를 인용하면 실패시킨다. JSON 내부 시각은 UTC, 사용자용 Markdown 표시는 KST다.

성공 시 개인 저장소에 `input.json`, `tool-audit.json`, `report.json`, `report.md`, `metadata.json`을 남긴다. 보고서에는 모델·프롬프트·도구·런북 버전, 계정 별칭, 가격표 날짜, 입력·출력 토큰과 추정 비용을 포함한다. 실패 시에는 사유와 확보한 조회 감사 기록, 받은 응답의 부분 사용량, 안전한 계약 오류 코드·필드 경로를 `metadata.json`에 남긴다. 응답을 받지 못한 호출은 비용 0으로 단정하지 않고 `complete_for_attempts: false`로 표시한다. 모델 응답 원문이나 API 키는 저장하지 않는다.

```sh
# 키를 처음 등록하거나 교체할 때 대화형 입력창에 붙여넣는다. 이 명령은 API를 호출하지 않는다.
./ai-ops/scripts/aiops-local configure-api-key
./ai-ops/scripts/aiops-local api-key-status

# 실제 유료 호출은 별도로 명시적으로 실행한다.
./ai-ops/scripts/aiops-local investigate \
  --mode ai \
  --bundle ai-ops/evals/fixtures/dev/s1-cache-error \
  --registry ai-ops/config/targets.example.json \
  --question "캐시 오류를 조사해줘" --request-id a5-s1-first
```

기본 개인 저장소는 Git 저장소 밖 `~/.local/share/url-shortener-ai-ops`이며 키 파일은 그 안에 0600으로 보관한다. 별도 경로를 쓸 때는 세 명령 모두에 같은 `--store`를 지정한다. `configure-api-key`는 네트워크 호출이나 키 유효성 검사를 수행하지 않는다. 모의 응답으로 도구 조회→실제 전달 ID 인용→보고서 재조회, 허위 인용 거부, 건당·일일 예산의 호출 전 거부를 확인했다. 이 시험은 모델 품질이나 외부 API 호환성의 증거가 아니다.

## 첫 실제 연결 점검: 2026-09-30

- 저장된 키로 `GET /v1/models/gpt-6-sol`은 HTTP 200이었다. 키 인증과 모델 메타데이터 조회가 가능하다는 의미이며, 생성 요청의 사용 가능 여부까지 보장하지 않는다.
- 합성 `s1-cache-error` 조사 두 건은 모델 생성 전에 실패했다. 첫 실행은 HTTP 429를 모두 재시도하던 코드에서 `model_retry_exhausted`, 오류 분류를 보완한 두 번째 실행은 `model_credit_balance_exhausted`를 기록했다. [OpenAI 공식 오류 문서](https://developers.openai.com/api/docs/guides/error-codes)는 `credit_balance_exhausted`를 조직의 선불 크레딧 잔액 부족으로 설명하며, 결제·한도 오류는 재시도만으로 해결되지 않는다고 안내한다.
- 두 실행 모두 증거 조회 도구 호출 0회, AI 보고서 없음, 저장된 실행 파일 내 API 키 노출 없음이었다. 키 파일 권한은 0600이다. 로컬 UTC 일일 예산 장부에는 건당 $0.10씩 **$0.20 예약**됐다. 이 값은 실제 청구액이 아니며 실패해도 예약을 돌려주지 않는 현재 정책을 따른다.
- 당시에는 실제 생성·도구 호출·근거 인용·사용량 기록을 검증하지 못했다. 같은 실패 요청 ID는 자동 재실행되지 않아 결제 후 새 ID로 재검증했다.

## 결제 후 합성 사례 재검증: 2026-09-30

- 첫 재시도는 모델이 없는 지표 ID와 증거에 없는 로그 컨테이너를 조회하는 바람에 세 번의 도구 호출 후 `case_budget_limit`로 중단됐다. 당시 버전은 실패 실행의 부분 사용량을 저장하지 않았다. 이 과거 실행의 실제 청구액은 API 사용량 화면에서 별도로 확인해야 한다.
- 지표 카탈로그에 허용된 `query_id`를 노출하고 모델 도구 스키마의 지표 ID와 로그 컨테이너를 제한했다. 이후 `s1-cache-error`를 새 요청 ID로 실행해 `query_service_metrics`의 `ev-s1-metric`, `get_pod_logs`의 `ev-s1-log`를 실제 제공하고 이 두 ID만 인용한 AI 보고서를 생성했다. 모델 오류 0회, 도구 호출 2회였다.
- 보고서는 **캐시 조회 타임아웃을 원인 후보**로 제시하고 Redis 자체 장애·네트워크 지연·설정 문제와 사용자 영향을 확정하지 않았다. 이벤트 권한 부족을 별도로 표시했고 조치는 실행하지 않았다. 이는 합성 저장 증거에 대한 결과이지 라이브 클러스터 진단이 아니다.
- 성공 실행의 모델은 `gpt-6-sol`, 사용량은 입력 5,885·출력 701토큰, 표준 단가 기준 **추정 비용 $0.018780**이다. 실제 청구액은 계정의 API 사용량 화면으로 확인해야 한다. 보고서·감사·입력 파일은 모두 0600이고 키 값은 실행 파일에 없다.
- 모델이 초안 일부에 UTC 시각을 썼으므로 사용자용 Markdown은 명시된 UTC 시각을 KST로 변환하도록 고쳤다. 저장된 JSON의 내부 시각은 UTC를 유지하고 기존 성공 실행의 `report.md`도 검증된 JSON에서 다시 생성했다. 날짜가 모호한 시각은 추정해 변환하지 않는다.

## 개발 사례 5건 결과: 2026-10-01

| 사례 | 최종 진단 | 도구 호출 | 추정 비용 | 사람 검토 |
|---|---|---:|---:|---|

| S2 정상 miss 후보 | 증거 부족 | 2회 | $0.018722 | 최초 보고서는 장애를 단정하지 않았으나 정상 miss 가능성을 명시하지 않아 부분 충족. 아래 재검증에서 보완 |
| S3 이미지 태그 | 원인 후보 | 2회 | $0.018068 | 배포 이미지와 ImagePullBackOff를 연결하고 실제 레지스트리 상태는 확정하지 않음 |
| S4 DB 관련 지연 | 원인 후보 | 2회 | $0.019032 | 앱 측 P99 0.9초·표본 120건과 ORM·주입 지연을 구분하고 DB 서버 장애는 확정하지 않음 |

S4·S5는 첫 시도에서 `invalid_ai_report`로 실패했다. 모델 응답 원문은 보관하지 않아 당시 계약 위반의 세부 필드는 확인할 수 없다. 이후 `a5-v2` 프롬프트에 **실제로 제공된 available 증거만 인용**, 증거 부족 시 빈 사실·가설, 진단 상태와 가설의 관계를 명시하고 재실행해 통과했다. 앞으로의 실패는 민감한 원문을 저장하지 않고 계약 구조·인용·지지 증거 오류를 구분해 기록한다. 이 수정은 두 사례에서 재현된 실패를 줄였지만 일반적인 모델 품질을 보증하지 않는다.
