# B-04 예약 보관 정리

현재 상태: **로컬 구현·예약 정리 시험 10건 통과, main 기반 전체 216건 통과 후 추가 runtime 시험 1건 통과, 새 이미지 등록·실제 배포 검증 전**이다. 기존 실제 worker는 아직 자동 보관 정리를 하지 않는다.

## 기능과 처리 흐름

worker가 수동 조사 한 건을 처리한 뒤 다음 요청을 가져오기 전에 만료 자료를 정리한다. 별도 CronJob이나 추가 Pod를 만들지 않고 기존 단일 worker 잠금 안에서 실행한다. 따라서 정리와 수집·보고서 저장이 겹치지 않으며 Kubernetes 쓰기 권한이나 다른 PVC 연결이 필요하지 않다.

**worker 시작 → 영속 예약 장부 확인 → 실행 기한이면 새 claim을 잠시 멈춤 → 만료·종료 후보만 최대 10건 선택 → 기존 삭제 계획으로 정리/재개 → 다음 실행·결과·순회 위치 기록 → 요청 처리 재개** 순서다.

## 실행 주기와 범위

- chart의 `retention.enabled=false`가 기본값이다. 검증한 새 이미지에 `config/b4-values.worker.yaml`을 명시하면 worker와 함께 예약 정리를 활성화한다. 진단 모드에서 활성화하는 설정은 schema가 거부한다.
- 기본 확인 간격은 60초이며 시작 시 처음이거나 실행 기한을 놓쳤으면 다음 안전 지점에서 즉시 확인한다. 요청을 처리 중이면 끝난 뒤 실행하므로 정확히 매 분 정각에 실행되는 작업은 아니다.
- 한 회차는 최대 10건, 작업 사이 시간 예산은 20초다. 한 파일의 동기 I/O를 강제로 끊지는 않는다. 더 남으면 다음 회차를 5초 뒤 예약한다. 오래 걸리거나 중단되면 삭제 장부에서 이어간다.
- 최초 접수 시각 + 7일 기한은 바꾸지 않는다. 만료된 completed/partial/failed/cancelled/needs_review 중 lease 없는 자료만 대상이다. 대기·실행 중 작업을 강제로 취소하거나 지우지 않는다.
- 자동 실행 시 실제 삭제는 `apply`이며 별도 회차별 사용자 승인은 요구하지 않는다. 이번 명시적 활성화가 해당 7일 정책의 실행 설정이다. 수동 CLI 기본값은 계속 미리보기다.
- 질문·고정 증거·연결된 모든 시도의 보고서/감사/인덱스는 기존 삭제 절차로 정리한다. 중복 해시 키·삭제 장부·API 키·예산·자체 관측·독립 수동 보고서는 보존한다.
- 보호해야 할 파일이나 불명확한 자료는 지우지 않는다. 순회 위치를 영속 저장하여 특정 문제 작업만 반복하다 다른 만료 자료가 정리되지 않는 상황을 줄인다. 불명확한 공통 파일은 여러 작업의 삭제를 차단할 수 있으므로 운영자 확인이 필요하다.

기한 도달 즉시 모든 바이트가 지워지는 보장은 아니다. 다음 안전 지점·배치 대기·파일 오류·미완료 작업 때문에 기한을 넘길 수 있으며 아래 overdue 지표로 확인한다. 이 기능은 큐 소유 자료의 논리적 정리다. 백업·WAL·매체의 과거 바이트 소거와 독립 B-02 보고서 전체 정리는 범위 밖이다.

## 중단·충돌·실패 처리

실행 시작을 SQLite의 `retention_schedule` 단일 행에 기록하며 완료 기록 전 프로세스가 종료되면 due 상태를 유지한다. 다음 worker는 기존 `purges` 계획에서 재개한다. 파일 삭제가 끝난 뒤 예약 결과 기록만 실패해도 완료된 자료를 다시 조사하거나 삭제하지 않는다. 예약 장부를 위해 기존 큐 schema v2를 바꾸거나 작업을 초기화하지 않는다.

다른 운영자 명령이 engine 파일 잠금을 잡고 있으면 기다리지 않고 `deferred`로 기록해 60초 뒤 다시 확인한다. 정리 중 SIGTERM은 파일 사이 안전 지점에서 멈추고, 신규 claim 없이 worker가 종료된다. worker의 실제 진행 상태 검사는 정리 진행 중에도 갱신된다. 파일 I/O 자체가 멈춰 진행하지 못하면 기존 liveness 검사와 삭제 재개 절차가 적용된다.

고정 코드 로그에는 `stage=retention`, `event=retention_finished/retention_deferred`, 결과와 소요 시간만 남긴다. 질문·경로·원문 예외·작업 ID는 넣지 않는다. 파일·소유권 오류는 partial/failure로 기록하고 다음 회차에서 다시 확인한다. 저장소 자체를 읽거나 결과 장부를 기록하지 못하면 정상 완료로 인정하지 않으며 worker가 실패할 수 있다.

## 지표와 운영자 확인

활성화하면 기존 31개에 다음 7개 gauge가 더해져 총 38개가 된다. 기존 ServiceMonitor 상한 50을 유지한다. 비활성 worker는 예약 지표를 제공하지 않는다.

| 지표 (`ai_ops_retention_` 접두사) | 의미 |
|---|---|
| `enabled` | 예약 정리가 현재 worker에서 활성화돼 있으면 1 |
| `next_run_timestamp_seconds` | 다음 확인 예정 UTC Unix 시각 |
| `last_success_timestamp_seconds` | 마지막 성공 배치 완료 시각. 전체 자료 준수의 보증은 아님 |
| `last_failure_timestamp_seconds` | 마지막 부분 실패 또는 실패 배치 완료 시각 |
| `last_run_purged_jobs` | 마지막 회차의 삭제 완료 작업 수 |
| `last_run_blocked_jobs` | 마지막 회차의 안전 검사 차단 수 |
| `overdue_jobs` | 7일 기한이 지났지만 jobs에 남은 자료 수. 미완료 작업도 포함 |

`up=1`만 보고 정리 성공으로 판단하지 않는다. overdue가 계속 증가하거나 failure 시각이 success보다 최신이면 작업 상태·파일 권한·삭제 장부를 운영자 CLI에서 확인한다. 지표 조회는 읽기 전용이며 정리를 시작하지 않는다. HTTP 관리 API나 자동 알림 규칙은 추가하지 않았다.

수동 미리보기/정리를 하려면 **같은 이미지·PVC를 유지하며 `mode=diagnostics`, `retention.enabled=false`를 함께 설정**한 뒤 worker 종료를 확인한다. 기존 `queue-retention` 명령을 사용한 뒤 worker overlay 값으로 복귀한다. 잠금 파일 삭제·DB 직접 변경·PVC 삭제로 충돌을 우회하지 않는다. 전체 인프라 정리 순서는 바꾸지 않는다.

## 검증

신규 10건은 예약 주기·재시작 후 다음 시각 보존, 미완료/미만료 보존, engine 사용 중 지연, 10건 배치와 문제 작업 이후 순회, 종료 신호의 안전 지점, 고정 38개 지표, 실제 별도 프로세스의 삭제 중 종료와 예약 완료 기록 직전 종료 후 재개를 확인한다. 기존 7일 정책·파일 보호·삭제 계획 시험도 함께 회귀 검증한다.

실제 배포에서는 기존 운영 자료의 시각을 바꾸지 않는다. 운영 큐에서 예약 실행·지표를 확인하고, 별도 임시 저장소의 합성 만료/미만료 취소 요청으로 자동 삭제·보존·재시작 후 주기 유지를 검증한다. 성공 시 본문 없는 실행 기록을 추가한다. 이 기능으로 B-05 경보 수신이나 외부 AI를 활성화하지 않는다.
