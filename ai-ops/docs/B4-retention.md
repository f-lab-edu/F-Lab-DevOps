# B-04 보관표·연계 삭제 — 두 번째 묶음

현재 상태: **로컬 구현·검증 완료, 클러스터 worker 배포 전**이다. 현재 진단 Pod나 실제 저장 자료는 변경하지 않았다. AWS·외부 모델을 호출하지 않고 합성 자료로 검증했다.

## 기능과 흐름

큐에 요청을 접수한 시각부터 7일간 보관하고, 만료된 종료 작업의 질문·고정 증거와 연결된 보고서를 함께 정리한다. 기본 실행은 보관표와 삭제 대상 미리보기다. `--apply`를 지정해야 삭제한다. 주기적 실행기나 CronJob은 아직 연결하지 않았다.

흐름은 **보관표 조회 → 미완료/기한/소유권 검사 → 삭제 계획을 DB에 확정 → 비공개 삭제 대기 경로로 이동 → 파일·인덱스 삭제 → 큐 질문·시도 삭제 → 본문 없는 완료 기록 유지**다. 삭제 중 실패해도 보고서를 새로 만들거나 조사를 재실행하지 않는다.

## 범위와 기한

- 기한은 최초 `created_at + 7일`이며 재시도·재조회·중복 접수로 연장하지 않는다. 상태·보관표 JSON 시각은 UTC다.
- 대상은 `completed/partial/failed/cancelled/needs_review` 중 lease가 없고 기한이 지난 작업이다. 대기·수집·분석 중 작업은 기한이 지나도 강제로 삭제하지 않는다. 운영자가 원인을 확인하고 필요하면 취소한 뒤 정리한다.
- 질문을 포함한 jobs row, attempts row, 고정 snapshot, 해당 시도의 engine input/report/audit/metadata·request index를 정리한다. 마지막 결과뿐 아니라 실패한 앞선 시도도 포함한다.
- 별도 수동 조사 등 큐 소유로 확인되지 않은 보고서, 다른 job, API 키, fingerprint key, 당일 예산 장부, 자체 관측 집계는 보존한다. 기존 A 평가 결과나 독립 B-02 수집 결과 전체를 청소하는 명령이 아니다.
- 중복 방지를 위해 episodes의 해시 키·job UUID와 purges의 기한·계획 해시·실행 UUID·완료 시각을 남긴다. 본문·질문은 삭제 장부에 복제하지 않는다. 삭제된 요청 키로 다시 접수하지 못하며 새 요청 키가 필요하다.

## 명령

새 코드가 포함된 worker 이미지를 배포하기 전에는 현재 클러스터 이미지에서 실행할 수 없다. 로컬에서는 등록된 저장소 경로를 지정한다.

```sh
# 기본값은 보관표와 삭제 대상 미리보기다.
python -m ai_ops queue-retention --store /data/incidents

# 특정 작업만 확인한다.
python -m ai_ops queue-retention --store /data/incidents --job job-실제반환ID

# 검토한 만료 작업 하나를 정리하거나 중단된 삭제를 재개한다.
python -m ai_ops queue-retention --store /data/incidents --job job-실제반환ID --apply
```

`keep`는 기한 이내, `would_purge`는 삭제 후보, `blocked`는 미완료 또는 안전하게 소유권을 확인하지 못한 자료, `purged`는 이번 정리 완료, `already_purged`는 이전 정리 완료다. `queue-show`에는 삭제 진행 중 `purging`, 완료 후 `purged`가 표시된다. 이는 jobs 처리 상태를 추가한 것이 아니라 삭제 장부에서 계산한 조회 상태다.

미리보기 exit 0은 명령 성공이지 모든 항목의 삭제 가능 판정이 아니다. 적용 중 blocked 항목이 있거나 DB 쓰기가 실패하면 exit 2다. 최대 1,000개 항목을 표시·처리하고 더 있으면 `truncated=true`로 알린다. 특정 작업은 `--job`으로 선택한다.

## 중단과 소유권 보호

worker OS 잠금과 engine 잠금으로 실행·게시·정리가 겹치지 않게 한다. 보관 조회는 engine의 자동 재조정을 실행하지 않는다. 다만 저장소 초기화·schema 전환과 잠금 파일 생성은 수행할 수 있다. 미리보기는 저장 자료를 삭제하지 않는다는 의미다.

삭제 계획과 SHA-256을 SQLite에 commit한 뒤 보고서 폴더를 `queue/expired/<job>/`로 옮긴다. engine이 삭제된 인덱스를 재생성하지 못하도록 원래 조회 경로에서 먼저 분리한다. 이동·삭제는 디렉터리 fsync를 거쳐 반영하고, 중단 후 같은 계획으로 남은 파일만 지운다. 파일 삭제 후 DB commit만 실패해도 다음 적용에서 재개한다.

링크·다른 소유자·공유 권한·예상 밖 파일·다른 요청을 가리키는 인덱스·변조된 계획은 차단한다. 소유 불명 큐 임시 snapshot이나 engine 미완성 파일도 임의로 지우지 않으며 운영자 검토가 필요하다. 오류를 없애려고 삭제 대기 경로나 장부를 초기화하지 않는다.

SQLite `secure_delete`를 사용하지만 파일시스템·WAL·백업·EBS snapshot의 과거 바이트를 복구 불가능하게 지우는 것을 보장하지 않는다. 현재 저장소에서 확인된 연결 자료의 논리적 정리이며 백업 보관 정책은 별도 책임이다.

## schema v1 → v2

첫 새 버전 큐 CLI 실행에서 하나의 transaction으로 v1에 `purges`를 추가하고 `user_version=2`로 바꾼다. 작업·시도·중복 키와 fingerprint key는 유지한다. 새 저장소도 v2로 생성하며 알 수 없는 버전은 거부한다. v1만 지원하는 이전 worker는 v2를 열 수 없다.

기존 큐가 있다면 worker를 중지하고 일관된 백업·복구 방법을 준비한 뒤 전환한다. WAL 상태에서 DB 하나만 복사한 것을 완전한 백업으로 취급하지 않는다. 현재 클러스터에는 B-04 큐 worker가 없으므로 이번 작업에서 실환경 schema는 전환하지 않았다.

## 검증과 다음 단계

전체 Python **199개**, 신규 보관 시험 **17개**가 통과했다. 7일 경계·미리보기·키/예산/다른 보고서 보존·실패 시도 전체 정리·중복 차단·lease 보호·worker 잠금·링크/계획 변조·v1 전환을 확인했다. 별도 프로세스가 파일 일부를 삭제한 뒤 강제 종료된 경우와 파일 삭제 후 DB 기록 실패도 재개에 성공했다. 자료는 저장소 밖 임시 합성 입력이며 시험 종료 시 제거한다.

다음은 queue/worker 지표·조회 접근 경계·명시적 배포 모드와 실제 Pod 재시작 복구다. 현재 단계는 예약 정리 실행, 실제 자료 삭제, worker 배포 또는 B-04 전체 완료를 뜻하지 않는다.

관련 파일: `src/ai_ops/retention.py`, `job_queue.py`, `incidents.py`, `cli.py`, `tests/test_queue_retention.py`.

## 연속 worker와 함께 사용할 때

[배포 worker](B4-worker-deployment.md)는 유휴 중에도 잠금을 유지한다. 같은 이미지·PVC의 진단 모드로 명시적으로 전환하여 worker 종료를 확인한 뒤 이 명령을 실행하고, 정리 후 worker 모드로 복귀한다. 잠금 파일 삭제로 충돌을 우회하지 않는다.
