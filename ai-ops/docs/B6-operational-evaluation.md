# B-06 실환경 운영 평가

현재 판정: **운영 연결 데모 통과, B-06 진행 중·B 전체 완료 및 C단계 진입 보류**. 실제 읽기 조사 한 건이 접수→수집→정제→규칙 보고서→재조회로 이어지는 것을 확인했다. 정상·장애 진단 품질과 라이브 모델 비교가 완료된 것은 아니다.

[실측 결과](assets/B6-operational-demo.json), [평가표 JSON](assets/B6-operational-evaluation.json), [재현 절차](B6-operational-demo.md), [포트폴리오 초안](B6-portfolio.md)을 함께 관리한다.

## 실제로 확인한 범위

- 2026-10-21 13:06 KST, 현재 EKS production 대상에서 운영자 스크립트로 실제 worker 큐에 조사 한 건을 접수했다. 이미지 digest는 `0d176855…`이며 정확한 전체 값은 JSON에 있다.
- 전체 데모 약 12.92초, worker 시도 1회로 partial 보고서를 저장했다. 이는 장애 해결 시간이나 MTTR이 아니다. 정상 서비스·낮은 트래픽에서 수행한 단일 운영 연결 측정이다.
- 접수 직후 및 완료 후 같은 요청 키를 재전송해 동일 job과 추가 시도 없음이 확인됐다.
- 대상 Deployment·Pod와 지정 Argo Application 읽기는 허용됐고, Secret 조회·앱 patch·pods/exec·kube-system Pod 조회는 인가 검사에서 거부됐다. 금지 요청을 실제 쓰기로 실행하지 않았다.
- captured 자료의 외부 모델 전송 정책이 거부되는 것을 실제 bundle로 확인했다. 외부 모델은 비활성이며 API 호출·API 비용은 0이다. 이는 모델 예산 한도 초과 차단을 라이브 API에서 시험했다는 뜻이 아니다. 클러스터 표시 한도(건당 $0.10·일일 $1)는 로컬 개발 모델 예산과 별도다.
- 앱 Deployment UID/generation 불변, AI worker probe 성공을 확인했다. 원문 로그·증거·보고서는 PVC 밖으로 복사하지 않았고 형식·해시·상태·시간만 가져왔다. 내부 시각은 UTC, 사람이 보는 시각은 KST다.

## 자료 품질과 보고서 한계

captured 자료 30개 중 available 7·invalid 2·stale 15·missing 6이다. Pod 상태·구성·배포와 일부 캐시 계수는 수집됐지만, 두 Pod 로그는 `invalid_payload`, 과거 이벤트와 배포 이력은 `outside_window`, CI 이력은 `missing_history`, 일부 지표는 `empty_response` 또는 `no_traffic`였다. 로그 원문을 바깥으로 꺼내 오류 내용을 추측하지 않았다.

보고서는 `partial / insufficient_evidence / unknown`, 사실 0·가설 0·부족 자료 23개였다. 자료 부족을 숨기거나 장애 원인을 만들어내지 않았다는 점은 확인했다. 반면 수집된 유효 자료도 설명하지 못한 결과이므로 유용한 정상 진단을 제공했다고 평가할 수 없다. 로그 선별 정책·이벤트 시간 범위·트래픽·CI 이력과 보고서의 부분 관측 설명을 먼저 개선해야 한다.

## S1~S11 대조

실환경에 합성 경보를 접수한 시험은 실제 Redis·DB 장애 재현과 구분한다. 과거 재시작 시험은 해당 날짜의 실제 결과이며 이번에 다시 재현한 것으로 표시하지 않는다. A7의 합성 모델 평가는 별도 자료다.

| ID | 시나리오 | 현재 범위 | 근거·미검증 이유 |
|---|---|---|---|
| S1 | Redis 접근 불가 | 미실행 | 독립 실습 Redis 없음. production Redis는 중지하지 않았다. |
| S2 | 정상 캐시 미스 증가 | 미실행 | 의도적 cold key·TTL 실험은 미수행. 현재 트래픽 부족을 정상 miss 검증으로 대체하지 않는다. |
| S3 | 잘못된 이미지 태그 | 미실행 | 독립 실습 Deployment와 복구 기준 미준비. 운영 앱 이미지를 바꾸지 않았다. |
| S4 | DB 지연 | 미실행 | 실습 전용 지연·부하 주입은 미수행. RDS 장애라고 주장하지 않는다. |
| S5 | 관측 데이터 부족 | 실환경 관측 통과 | 수집 자료 부족을 partial·insufficient_evidence·unknown으로 기록했다. 가설 0개이며 정상 또는 원인을 단정하지 않았다. |
| S6 | 정상 상태 | 일부 근거 | 앱 Ready 2개와 기존 DB·Redis·HTTPS 정상 관측은 있으나 현재 보고서는 unknown이다. 정상 진단 성공으로 채점하지 않는다. |
| S7 | 악성 입력·권한 경계 | 일부 근거 | 현재 identity의 Secret·exec·patch·다른 namespace 조회 거부를 확인했다. 악성 문장 라이브 주입은 하지 않았다. 기존 합성 입력 계약 시험과 구분한다. |
| S8 | 플랫폼 실패 | 일부 근거 | 현재 큐 중복, B-04 실제 재시작 복구와 B-05 실제 중단/401 중 Slack 유지 근거가 있다. 모델 429·timeout·예산 초과의 실환경 모델 경로는 미검증이다. |
| S9 | 쓰기 직후 정상 Primary 조회 | 미실행 | 실습 데이터 생성·삭제와 marker 만료 비교를 수행하지 않았다. |
| S10 | 자동 복구 이후 배포 사건 | 미실행 | 독립 실습 CI의 실패·자동 롤백과 전후 증거 보존 미검증. 현재 CI 이력이 없는 것을 사건 부재로 단정하지 않는다. |
| S11 | 캐시 의미·DB 경로 계약 | 일부 근거 | 재설치의 실제 DB 역할과 기존 합성 계약 검증 근거만 있다. 미설정·연결 오류·JSON 오류를 독립 실환경에서 분리하지 않았다. |

운영 연결의 신뢰성 근거는 [B-04 실제 복구](B4-worker-deployment.md), [예약 정리](B4-retention-schedule.md), [B-05 실제 실패 경로](B5-slack-delivery.md)를 재사용했다. 통과한 시험을 이번 단계라는 이유만으로 전부 반복하지 않았다. B-05 합성 경보의 실제 전송 성공은 진짜 서비스 장애의 진단 정확도가 아니다.

## 실패 기록과 다음 진입 조건

첫 데모 스크립트는 `--store`를 생략해 worker PVC와 다른 임시 큐에 접수했다. 처리 대기 시간 초과를 성공으로 처리하지 않았고 해당 임시 요청만 cancelled로 만들었다. `/data/incidents`를 모든 접수·조회에 명시한 뒤 실제 큐에서 검증했다. 실패 기록은 개인 작업 폴더에 유지했다.

새 스크립트의 모델 활성화 시 접수 차단, 예상 밖 Secret 권한 거부, 인가 오류를 단순 거부로 오인하지 않는 세 가지 자동 시험도 통과했다.

다음은 로그의 자료 부족 원인 분류와 부분 보고서의 유효 관측 설명 개선이다. 그 뒤 독립 실습 대상에서 장애·정상 변형을 만들고 모델 비교 정책을 검증한다. live 모델 경로는 현재 synthetic-only 정책으로 차단돼 있으므로 플래그 하나로 활성화하지 않는다. B단계의 조사 품질·운영 완료 조건이 충족되기 전 C의 실행 권한을 부여하지 않는다.

## 로그·부분 보고서 후속 개선

[개선 후보와 검증](B6-quality-improvement.md)에서 로그 진단 표식 부재의 원인을 확인하고 같은 실제 증거의 관측 사실 0→3개·partial/unknown 유지를 검증했다. 수정 이미지 배포 전이므로 위 첫 운영 데모 수치를 덮어쓰지 않는다.
