# B단계 포트폴리오 초안 — 검증한 범위만 표현

현재 상태: 운영 연결과 경계 검증은 가능하다. 라이브 LLM 진단 정확도·MTTR 개선·운영 장애 자동 해결을 성과로 주장하지 않는다.

## 프로젝트 설명

EKS의 URL 단축 서비스를 대상으로 Kubernetes·Prometheus·Argo CD의 운영 자료를 읽고, 정제된 증거와 조사 보고서를 영속 보관하는 운영 조사 시스템을 구성했다. Alertmanager 경보와 수동 요청을 큐에 연결하고 최소 권한·네트워크 제한·중복 방지·재시작 복구·보관 정리를 구현했다. 기존 Slack·Watchdog 분기는 독립적으로 유지한다.

조사 요청이 자료 수집·증거 고정·규칙 보고서로 이어지는 실제 운영 데모를 확인했다. 자료가 부족하면 partial과 판단 유보를 남기고, 비밀 읽기·운영 변경·captured 자료의 외부 모델 전송을 차단한다. 별도 A단계의 합성 모델 평가와 현재 production 규칙 보고서를 구분한다.

## 검증 사례

- AI 실패가 사람 알림을 막는지 확인하던 중 Slack `channel_not_found`를 발견했다. 같은 Webhook의 기본 채널은 성공함을 확인하고 고정 채널 지정을 제거했다. AI 중단 및 실제 401 중에도 Slack 성공을 확인하고 원상 복구했다. [사례](B5-slack-delivery.md).
- 실제 읽기 조사 한 건은 약 12.92초에 처리됐으며 전후 중복 접수에도 시도가 추가되지 않았다. 수집 자료 30개 중 7개만 유효한 결과를 숨기지 않았고, 보고서는 원인을 단정하지 않았다. 12.92초는 이 단일 데모의 전체 실행 시간이며 MTTR이 아니다. [평가](B6-operational-evaluation.md).

## 이력서 문장 예시

> EKS 읽기 전용 운영 조사 파이프라인을 구축하고 경보 접수·영속 큐·증거 정제·규칙 보고서·중복 방지·복구·보관 정책을 연결했습니다. AI 수신기 중단·인증 실패 중 기존 Slack 전달 유지와 운영 자료의 외부 전송 차단을 실환경에서 확인했습니다.

## 아직 주장하지 않는 내용

라이브 LLM 진단 정확도, 운영 장애 원인 적중률, MTTR 절감률, 비용 절감률, 실제 운영 장애의 자동 해결은 미검증이다. 현재 자료는 단일 production 읽기 데모·일부 실환경 경계 시험·별도 합성 평가로 구성된다. 독립 실습 시나리오와 모델 비교를 완료한 뒤 문구를 갱신한다.
